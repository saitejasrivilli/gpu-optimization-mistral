# Scheduling engine (Phase 3)

Package: `internal/scheduler`. Depends only on `internal/domain` and stdlib. Pure and deterministic: never mutates its inputs, never performs infrastructure operations, never depends on NVIDIA/CUDA/Kubernetes/Docker/HTTP/Prometheus.

## Workload requirements

`domain.WorkloadRequirements` (added in Phase 3, `internal/domain/workload_requirements.go`):

| Field | Used by | Purpose |
|---|---|---|
| `WorkloadID` | all | correlates a `Placement`/failure back to the requesting workload |
| `GPUCount` | all | how many GPUs, all on one worker (see Topology below) |
| `MinGPUMemoryBytes` | compatibility, BestFit | minimum capacity *per selected GPU* — requirements are per-GPU because an Allocation grants whole GPUs, not fractional memory |
| `CUDARequirement` | compatibility | minimum CUDA compute capability |
| `TopologyRequirement` | compatibility, TopologyAware | hard gate (`NONE`/`SAME_NODE`/`NVLINK_GROUP`) |
| `Priority`, `Preemptible` | none yet | carried for a later preemption phase; no Phase 3 policy reads them |
| `WorkloadType` | none yet | free-form classification for future routing/labeling |

## Compatibility vs. ranking

Compatibility ("can run") is evaluated once, before any policy sees the data: `eligibleWorkers` (compatibility.go) walks the snapshot in deterministic (WorkerID, then GPUID) order and produces, per worker, the GPUs that individually satisfy `AllocationState == FREE`, `Validation.Status == PASSED`, `Capability.MemoryBytes >= MinGPUMemoryBytes`, and the CUDA requirement — plus a `RejectedAlternative` for every GPU/worker that failed, with a specific reason. A worker only becomes a `WorkerCandidate` if it has enough eligible GPUs (and, for a hard NVLink requirement, a group big enough).

Ranking ("best place to run") happens only among already-compatible candidates, inside each policy. No policy re-checks compatibility.

## CUDA comparison

`cudaSatisfies(want, have)` normalizes both strings to a major.minor float (`"sm_80"` and `"8.0"` are treated as equivalent) and requires `have >= want`. If either side fails to parse, it falls back to exact string equality rather than guessing — deliberately conservative given simulated and real agents currently report capability in different conventions (see docs/agent.md).

## The scheduler interface

```go
type Scheduler interface {
    Name() string
    Place(ctx context.Context, req domain.WorkloadRequirements, snapshot domain.ClusterSnapshot, now time.Time) (Placement, error)
}
```

`Place` is pure: no policy holds mutable state, and `ClusterSnapshot`/`GPUSnapshot`/`WorkerSnapshot` are plain value types (no pointers/slices-of-pointers), so a caller's copy can never be mutated by a `Place` call — verified by `TestInvariant_SchedulerNeverMutatesSnapshot`, which runs all four policies concurrently against one snapshot and deep-compares before/after.

## Placement

```go
type Placement struct {
    WorkloadID, WorkerID string
    GPUIDs               []string
    Policy               string
    Score                float64
    Reason               string
    RejectedAlternatives []RejectedAlternative
    Timestamp            time.Time
}
```

`Reason` is always a deterministic, human-readable sentence generated by the policy's own logic — never an LLM call. `RejectedAlternatives` (also present on `Placement`, and forming the diagnostic backbone of a failed `*SchedulingError`) always explains *why*, never just returns a bare failure.

## The four policies

All four select from exactly one worker (see "Single-worker allocations" below) and share the same compatibility gate; they differ only in how they pick among compatible options.

1. **FirstFit** — first candidate worker (lowest ID), first usable GPU pool (see NVLink grouping below), first `GPUCount` GPUs in ID order. Baseline: fastest, worst fragmentation by design (see `TestFirstFit_PicksFirstEligibleRegardlessOfFitOrUtilization`).
2. **BestFit** — across all candidates, the `GPUCount`-GPU subset with the smallest total leftover capacity (`sum(GPU.MemoryBytes - MinGPUMemoryBytes)`), selecting the smallest-memory eligible GPUs first. Tie-break: worker ID, then GPU ID.
3. **UtilizationAware** — across all candidates, the subset with the lowest average `GPUState.UtilizationPercent`, using utilization already present in the snapshot (no new telemetry is created). Tie-break: worker ID, then GPU ID.
4. **TopologyAware** — prefers a subset entirely within one NVLink group (cohesion score 1.0). A single-GPU request always scores 1.0 (nothing to connect). See Topology below for the fallback when no group is big enough.

## Topology representation and fallback

`domain.GPUTopology{NodeID, NVLinkGroup}` is static, discovered data (see docs/agent.md) — the scheduler never assumes NVLink/NVSwitch/InfiniBand/RoCE exists. Two GPUs are "connected" only if they report the same non-empty `NVLinkGroup`; an empty value means unknown, and unknown GPUs are never treated as connected to each other.

- **Hard requirement (`TopologyNVLinkGroup`, compatibility gate)**: a worker is only a candidate if it has an NVLink group with at least `GPUCount` eligible members. `GPUCount == 1` always passes trivially. If no such group exists, the placement fails with `ErrIncompatibleTopology`, carrying every rejected alternative — never invented.
- **Soft preference (`TopologyAware` policy, ranking only)**: even with no hard requirement, `TopologyAware` still prefers a same-group subset when one is big enough. When none is (including when topology is entirely unknown), it falls back to the tightest-fitting subset from the whole eligible pool and reports the honest cohesion score for what it actually picked (0.0 when nothing shares a group) — never claims connectivity it didn't observe.
- **`TopologySameNode`**: always satisfied. An `Allocation` (domain package) is always scoped to a single worker, so every placement this scheduler produces is already "same node" by construction — see "Single-worker allocations" below.

## Single-worker allocations (a Phase 1 constraint, not new)

`domain.Allocation.WorkerID` is a single string, not per-GPU. That was set in Phase 1, before a scheduler existed, and it means this domain model has no way to represent a workload spanning multiple workers/nodes. Phase 3 policies work within that constraint rather than around it: every `Placement` selects GPUs from exactly one worker. Multi-node placement (and the "inter-node network tier" topology field docs/architecture.md mentions) is explicitly future work, consistent with that document's "Future integration points" section — not something this phase silently drops.

## Scheduling failure

`*SchedulingError` (errors.go) always carries `WorkloadID`, a human-readable `Reason`, and the complete `Rejected []RejectedAlternative` list. `errors.Is` works against one of: `ErrNoEligibleWorkers`, `ErrInsufficientGPUs`, `ErrInsufficientMemory`, `ErrIncompatibleCUDA`, `ErrIncompatibleTopology` — chosen by inspecting the *specific* (per-GPU) rejection reasons; when they're not uniform, the generic `ErrInsufficientGPUs` is used rather than guessing. A failed `Place` call always returns a zero-value `Placement` — never a partially-filled one (`TestAllPolicies_FailedSchedulingProducesNoPartialAllocation`).

## Determinism

Every internal traversal is explicitly sorted (`sort.Slice`/`sort.Strings` on worker ID, GPU ID, or NVLink group key) before iteration — nothing relies on Go map iteration order for anything that affects the output. Every "pick the best of several equally-scored options" tie-break falls through to `idSliceLess` (worker ID, then GPU IDs lexicographically), so two runs with the same snapshot and requirements always produce the same `Placement` (`TestAllPolicies_DeterministicOrdering`, `TestAllPolicies_EqualScores_StableTieBreak`).

## Benchmark methodology

`internal/scheduler/scheduler_bench_test.go`'s `BenchmarkScheduler` measures all 4 policies × 4 fleet sizes (8/16/32/64 simulated GPUs, `genFleet`, seed 42) × 3 batch sizes (100/1,000/10,000 placement requests per batch), reporting `ns/op` (per full batch) and a derived `placements/sec` custom metric. Every workload in a batch requests exactly 1 GPU with no other requirement, so every combination is schedulable at every fleet size — the benchmark isolates scheduler cost, not exhaustion behavior (fragmentation/exhaustion is exercised by the unit tests instead, e.g. `TestAllPolicies_FragmentedCapacity`).

Run: `go test -run xxx -bench . -benchtime=2x ./internal/scheduler/...`

Results are written to `benchmark/results/scheduler-policy-latency-throughput.json`, generated mechanically from an actual run's stdout (never hand-edited), per docs/benchmark-plan.md's convention. See that file for the seed, fleet model, and every raw `(policy, fleet size, batch size) -> (ns/op, placements/sec)` measurement.
